# 变更、审阅与验收证据

这是框架维护与项目实例化的指导。项目采用时将适用要求吸收到已有 workflow / 评审约定；不强制新建台账、CI、发布流程或顶层文件。普通修复不触发完整 Harness 维护。

## 1. 先定位实际执行路径

规划和审阅先确定用户入口、配置 / 状态、调用方、转换、实际执行方及结果。插件与内置、缓存与实时、平台分支可能由不同实现负责，修改必须到达用户实际使用的路径。

对复杂子系统可选用 [子系统模板](../templates/docs/subsystem.template.md)，已有 Owner Doc 时补在原处。职责、接口、状态、运行路径、失败和兼容行为变化时，在同一变更更新契约；源码链接和符号辅助核对，不复制易变实现。提案与当前事实分开。

每项语义变更说明“什么条件下，之前怎样，现在怎样，哪些邻近情形不变”，引用契约、实现与证据。Review 追踪相关调用和状态转换，不只看 diff 的几行。

## 2. 修复必须能被回归检查区分

存在行为回归风险的修复，优先使用报告者的真实输入或已批准 fixture，验证同一检查在修复前产生目标行为失败、修复后通过。只回退目标实现，保留测试和必要工具 / fixture；在临时副本或自己的 worktree 操作，不覆盖用户未提交内容。

编译失败、依赖失败、跳过或无关错误不能算修复前的证明。验证后恢复实现并清理自建探针。不能安全回放旧实现时写明原因、替代证据及未验证范围，不伪造 red → green，也不自动降低已有门禁。测试强度与需求正确性分开：新测试仍不能成为关键 Behaviour 的唯一验收依据。

搜索同类调用方、分支和派生值，记录共同根因覆盖了哪些路径、哪些不应改变；按风险扩大检查。涉及共享接口、配置读取、路由或公共样式时，考虑调用方与相关集成检查；不将所有任务升级成全量测试。

## 3. 普通任务也绑定证据版本

在既有任务 / PR / CI 记录中保留：

- 检查对象：代码 commit；未提交时记录 base commit 与可追溯 diff / 快照。相关配置、契约、输入 / fixture 及工具版本按风险记录。
- 验证：命令、环境、结果 / 证据位置；PASS、FAIL、ERROR、未运行、不适用分别报告。
- Review：审阅的版本，以及修复、复验后的结论。

相关实现、契约、配置或输入改变后，重新判断旧证据是否适用，补受影响的检查与 review；纯记录变化不要求无差别全量重跑。不要让“CI 全绿”指向不相关的旧版本。

已经授权的合并，核对实际合入版本与被审阅版本一致，并验证项目要求的整合结果；支持的平台使用 head 校验等保护。新 head 的相关变化重新审阅。没有合并、部署或发布授权就停在对应动作前，不因补记录获得额外权限。Tag、构建完成和实际发布分别确认。

## 4. 环境与覆盖按风险记录

仅有平台、浏览器、语言或真实客户端差异时，在既有证据中写适用组合、实际运行组合和未覆盖项，不建立空矩阵。交叉编译证明可构建，mock 证明受控条件下的行为，不能替代目标平台 / 原生容器 / 真实客户端的验收。

测试隔离 HOME / 用户配置目录、凭证、代理和系统工具；复用项目已有测试工具。后台进程和异步任务随测试收尾，网络依赖用固定 fixtures。真实系统验证单独说明授权、隔离和边界，不给通用框架硬塞特定语言的 sandbox。

## 5. 框架自身的验证边界

`scripts/test-instantiation.py` 实际渲染 minimal、根目录 product 模板及其裁剪组合，并探测标记保留、未填字段、失效锚点和源码链接。字段填充值仅供结构检查，不是实际业务规格。

`validate-instantiation.py` 只检查可达文档、占位符、文件和 Markdown 锚点；不解析源码符号、不证明运行路径和业务语义。工具指针与门禁由各自现有检查覆盖。Skill 模型 A/B、真实目标项目收益和未运行平台不能用本仓自检替代。
